# 全网证据核验单条试点 · 实现任务书（2026-11-20）

> 依据：`reviews/2026-11-19/zhihu_top15_optimization_plan_审查修订版_2026-11-19.md` §3（试点规范）与冲刺顺序第 3 项
> 前置状态：✅ 已完成——第 1 项恢复与验收（DeployId 034）；第 2 项配额守卫（`app.py` QuotaGuard，`web_search` 类目已预留、默认 0 = 禁用）
> 本任务书性质：实现规格 + 验收清单，队友可照此直接开工

## 0. 目标（一句话）

让 **1 条 `type=verify` 且 gap 有效** 的热点，在后台产出 0–1 条**来自真实全网搜索接口原始返回**的站外材料，并在卡片上以诚实文案展示；接口失败、无结果、配额触顶都有明确、可测试的降级路径。

## 1. 开工前必须核实的两件事（不做猜测）

1. **接口事实**：到知乎数据开放平台文档（developer.zhihu.com/docs）确认「全网搜索」的真实 endpoint、请求参数、返回结构与错误码，把结论（路径 + 字段截图/摘录）写进本文件 §1 的回复区。配额口径（5000 次/用户/天）已核实，路径未核实前不得写死进代码。
2. **环境变量**：`QUOTA_WEB_SEARCH_DAILY` 默认 0（完全禁用）。试点部署前由负责人在 CloudBase 控制台把它调大（建议先 20/天：单条试点 + 补跑冗余足够），否则守卫会拦截一切全网搜索调用——这是设计行为，不是 bug。

## 2. 允许的行为边界（§3.1 硬约束）

- 每份简报**只选 1 条** verify 热点做核验（第一条满足条件的即可，不择优、不循环）；
- 每次只展示 **0–1 条**站外结果；
- 全过程在**后台**完成：复用现有 stale-while-revalidate 链路（`generate_and_cache` → `build_brief`），**不得增加首屏等待**；
- 接口失败时**保持现有页面结构完全不变**（不显示核验区块）；
- 不满足条件（非 verify、gap 无效、接口 403/429/超时、结构缺字段）→ 直接跳过，**不补选、不降级为虚假结果**；
- 同一热点在同一次生成中**不重复发起**全网检索（首轮与收尾补跑之间用内存标记去重；跨进程不保证，可接受，须在代码注释里写明）；
- 大模型**不得生成任何站外 URL**；站外链接只能来自接口原始返回。

## 3. 数据契约（§3.2，逐字段落地）

每条站外结果落缓存前必须包含：

| 字段 | 规则 |
|---|---|
| `query` | 实际检索词（用热点标题 + gap 关键词拼装，原样保存） |
| `title` | 接口原始标题，不改写 |
| `url` | 接口原始链接；**必须 http(s) 且通过主机名白名单之外的独立校验**（至少 scheme+host 合法、非知乎域名——站内链接已由 reading 承担，不得重复） |
| `source` | 接口原始来源名 |
| `published_at` | 仅当接口返回时保存 |
| `snippet` | 仅当展示摘要时保存，且必须是接口原文；任何改写须另存 `snippet_edited: true` |
| `checked_at` | 本次核验时间（`now_str()`） |
| `status` | `found / no_result / error / skipped` 四值之一，必须落盘 |

缓存层建议：挂在该 item 下的 `web_evidence` 字段（对象，可空），不动现有六字段与 digest 结构。

## 4. 文案（§3.3，只许用这一版）

无结果时展示：

> **本次全网检索未返回可用的一手材料｜核验截至 YYYY-MM-DD HH:mm**

**禁止**使用的表述（会让「没有搜到」变成新幻觉）：

- 「全网没有」「不存在相关材料」
- 「权威媒体均未披露」「全网核验无公开材料」

找到结果时展示：标题 + 来源 + 核验时刻，标题链接可点；并在区块角落标注「检索词：xxx」，保证可复现。

## 5. 代码改动点（全部在既有结构内，不新增服务）

1. `app.py` 新增 `api_web_search(query)`：走 `zhihu_get` 同款鉴权与错误处理；入口先过 `_QUOTA.attempt("web_search")`，被拦直接抛 `UpstreamError("全网搜索当日配额已达上限（配额守卫）")`。
2. `app.py` `process_item()`：在 type 判定为 verify 且 gap 非空时，生成 `web_evidence`；任何异常只影响该字段，**绝不使该条降级**（站内内容已生成成功，核验是增强不是依赖）。
3. `demo/index.html`：verify 卡片 gap 下方渲染 `web_evidence` 区块（找到/无结果两种态），字段缺失或 status=skipped/error 时不渲染该区块；移动端不断行溢出。
4. 不改 `build_digest` 的计算逻辑（digest 仍只由站内字段确定性计算）；如要在今日洞察提及核验条数，必须单独评审，默认不做。

## 6. 回归测试（§3.4 七项，新增 `tests/test_web_evidence.py`）

1. 接口返回 1 条有效结果 → item 落 `web_evidence.status=found` 且字段齐全；
2. 接口返回 0 条 → `status=no_result`，且渲染文案严格等于 §4 句式；
3. 接口 403 / 429 / 超时 → `status=error`，页面结构不变、该条不降级；
4. 返回结构缺 `url` 或 `title` → 丢弃该条，`status=error`，不渲染；
5. 首轮失败后的收尾补跑**不重复发起**全网检索（守卫计数或内存标记证明）；
6. 全网搜索失败时，卡片原有站内 gap 与降级文案原样保留；
7. `QUOTA_WEB_SEARCH_DAILY=0`（或计数达上限）时自动跳过，`status=skipped`，无任何上游请求。

沿用现有测试风格：独立脚本、显式 assert、逐脚本运行；完成后 README 与计划书测试清单同步为「十二项 Python」。

## 7. 验收流程（照 HANDOFF 纪律执行）

1. 本地：六项既有 Python 相关测试不回归 + 新 7 项全 PASS；

5. 记录实际 DeployId、取样时刻与回滚点（届时当前为 034，回滚点 033）。

## 8. 明确不做（本期边界）

- 不扩到多条热点、不做全量 verify 核验；
- 不做定时/主动核验，仍走访问触发的惰性刷新；
- 不引入新的前端框架或构建链；
- 不把站外材料计入延伸阅读 2 条上限（那是站内白名单链路）；
- 不在计划书/答辩中使用「全网核验」「权威认证」类表述，除非有带时刻的真实快照支撑。

## 9. 回复区（实现者填写）

- 接口核实结论（endpoint / 参数 / 返回结构 / 错误码）：
  已按 §1 要求从官方文档直接核实（来源：`https://developer.zhihu.com/console/api/v2/docs` 文档 JSON，2026-11-20 19:00 抓取；另与开源社区实现 kids0cn/ai-agent-zhihu-skill、dsh-zhihu-search 交叉一致）：
  - Endpoint：`GET https://developer.zhihu.com/api/v1/content/global_search`（与热榜/站内搜索同 Base，Bearer 鉴权 + X-Request-Timestamp）。
