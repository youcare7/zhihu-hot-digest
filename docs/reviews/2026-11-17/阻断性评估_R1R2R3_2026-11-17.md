## 1. R1 · #10 整卡降级

### 1.1 现象（19:59 快照实测）

第 10 条全字段为降级哨兵，且**六个字段同时降级、彼此一致**：

```
rank: 10   type: 'verify'   claim_type: ''
title: 校招进了一个大公司新成立的部门，只有自己一个人，且直接跟大领导汇报，求经验？
background: '暂无解读。'       ← NO_BACKGROUND 哨兵
focus:      '暂无聚焦问题。'    ← EMPTY_FOCUS 哨兵
consensus:  ''                 ← EMPTY_CONSENSUS（本就允许为空）
gap:        '暂无可补的拼图。'  ← EMPTY_GAP 哨兵
sides: []   reading: []
```

### 1.2 根因

降级形态与 `process_item()`（app.py:421-488）的**初始 item 字典完全逐字段相等**，说明 `try` 块在**第一步就抛异常**，没有任何字段被覆写：

```python
candidates = fetch_search(title, rank)
if not candidates:
    raise UpstreamError("搜索无候选回答，按 FR-07/FR-04 降级")   # ← app.py:448
```

判据有三，互相印证：

1. **若失败发生在模型调用之后**，`background/focus/gap` 中至少有一个会被部分覆写；实测六字段全为原始哨兵，排除「模型返回残缺」。
2. **若是模型输出非法 JSON**（`extract_json` 抛错，app.py:309），同样会停在哨兵态；但此时其余 9 条同批次调用均成功，同一模型同一轮次独独第 10 条解析失败的概率低，且日志口径不同。
3. **题目性质吻合**：#10 是个人职场求助帖（"校招进了新成立部门，只有自己一个人"），属于**经验征集型**而非事实争议型。`api_search` 以完整标题作 Query（app.py:211-215），这类长口语化标题在站内搜索命中率天然低，`Data` 为 null 或 `Items` 为空时返回空列表 → 触发 448 行降级。

**最可能根因：上游 `zhihu_search` 对该长口语标题无候选返回，命中 FR-07/FR-04 既定降级路径。**

### 1.3 为何「补跑未恢复」

这**不是**补跑逻辑失效，而是 `_background_refresh()` 的防劣化保护按设计生效（app.py:849-862）：

```python
if old_ok > 0 and new_ok < old_ok:
    _log("刷新结果劣于现有缓存，丢弃本次结果，沿用旧缓存")
    return
```

`_count_ok()` 只统计 `background != NO_BACKGROUND` 的条数。补跑若仍是 9 条成功，`new_ok == old_ok`，**不触发丢弃**、正常覆盖，但第 10 条依旧无候选 → 结果看起来「没恢复」。即：**补跑真的跑了，只是上游依旧没有素材**。这与「宁留旧全绿，不覆新残次」的既定策略一致。

### 1.4 阻断性判断：**否**

- 这是**产品设计内的正确行为**，不是崩溃、不是数据错误、更不是幻觉。系统在无素材时选择"坦白说没有"，而非编造背景与 gap——这恰好是本产品「防幻觉」卖点的正向证据。
- 用户可见后果：10 张卡中 1 张显示"暂无解读"，其余 9 张完整；页面不报错、不白屏、digest 计数自洽（脚本已验 3/3/4）。
- **修复它反而有风险**：无论是放宽 `Query`（截断标题取关键词）还是对空候选重试，都属于改检索策略 = 扩功能，违反红线③，且会引入新的未验证行为。

### 1.5 建议处置

- 评审期**不修**。
- 答辩时这是**加分项不是减分项**，建议口径：「无站内素材时我们宁可留白也不让模型编造，这是四道防幻觉守卫的最后一道。」（建议同步进 `docs/答辩问答手册.md`，由 1 号决定是否补入）
- 赛后可选项：当 `Items` 为空时，用标题前 N 字或去除疑问词后重试一次搜索（**需单独验证，不进本次提交**）。

## 2. R2 · 字段硬截断

### 2.1 实测（19:59 快照全字段扫描）

扫描所有 `len(字段) == 上限` 的情况，共 **6 处触顶，其中 5 处非标点收尾 = 确认硬断句**：

| 位置 | 字段 | 上限 | 结尾 | 判定 |
|---|---|---|---|---|
| #2 | consensus | 80 | …`或关注声明，网传"已撤稿"不` | ❌ 断在词中 |
| #2 | gap | 100 | …`网及Retraction W` | ❌ 断在英文词中 |
| #9 | focus | 60 | …`"逼氪致停服"与官方"` | ⚠️ 收于引号但语义未完 |
| #9 | consensus | 80 | …`客服称2026年1` | ❌ 断在数字中 |
| #9 | reading.reason | 30 | …`退款与资产处置的规则参` | ❌ 断在词中 |
| #9 | reading.reason | 30 | …`列出可执行动作与时间` | ❌ 断在词中 |

> 注：19:47:58 预审报告记录的触顶点在 #1/#2/#5/#7，与本次 #2/#9 **不是同一批**。这说明**截断位置随每次生成漂移**，但「会发生截断」这一性质是稳定的。两份记录分时点保存，互不覆盖。

### 2.2 根因（确认为系统性，非偶发）

```python
def _clip(value, limit: int) -> str:
    """按字符数截断，并去掉首尾空白。"""
    return str(value or "").strip()[:limit]      # ← app.py:376-378
```

`_clip()` 是**纯字符切片**，无句读边界感知。它被 6 处调用（background 150 / focus 60 / consensus 80 / gap 100 / side.label 12 / side.claim 80 / reading.reason 30），且 PROMPT 要求的字数与这些硬上限**没有强绑定校验**——模型一旦写超，程序就从第 N+1 个字符处一刀切。

因此：**只要模型输出长度触顶，必然产生断句**。这是确定性行为，不是概率性 bug。

### 2.3 阻断性判断：**否**

- 影响是**可读性瑕疵**，不是事实错误：被截断的内容本身正确，只是尾部不完整。
- 不影响：JSON 结构（脚本 PASS）、三态分类、链接合规（17 条全知乎域名）、digest 计数自洽。
- 风险敞口可控：10 条中触顶字段为个位数，且多集中在信息量大的条目。

### 2.4 建议处置（赛后项，已在 TODO 登记）

两个方案，**不在评审期执行**：

- **方案 A（低风险）**：`GAP_MAX` 100 → 120，其余上限同步放宽 20%。只改常量，但治标不治本，仍会在新上限处断。
- **方案 B（推荐，治本）**：`_clip()` 增加句读回退——超限时向前回溯到最近的 `。！？；` 边界截断，找不到边界再退化为字符切，并在尾部补 `…`。改动集中在单个函数，**但需要回归三项既有测试 + 重新跑一轮真实生成验收**，时间成本不符合评审期约束。

## 3. R3 · 乱码（U+FFFD）

### 3.1 实测：**19:59 快照中已不存在**

对 10 条全字段（含 title/background/focus/consensus/gap/sides/reading）扫描 U+FFFD，**命中 0 处**。

19:47:58 预审报告记录的那处在 #5 consensus：

```
…增速慢、扩产收益多被人��增长吸收。
```

按上下文（该条讲人口与技术增长）应为「**人口**增长」，即「口」字位置出现 2 字节替换字符。

### 3.2 根因

U+FFFD 是**解码失败的替换字符**，不是模型生成的。可能来源有二：

1. **上游污染（最可能）**：`build_candidates_text()` 把搜索结果的 `ContentText` 截前 80 字喂给模型（app.py:321）。该截断是**字符级**的，但若上游返回的正文本身已含替换字符（知乎回答中的特殊符号、emoji 或编码异常），会被原样带入 PROMPT，模型再照抄进输出。
2. **解码路径**：`app.py` 主链路用 `decode("utf-8")` 严格解码（app.py:190/229），遇非法字节会**抛异常**而非产生 U+FFFD；而 `scripts/smoke_check.py` 用 `decode("utf-8", "replace")`（宽松替换）。因此 **U+FFFD 更可能来自上游数据内容本身，而非本地解码环节**。

### 3.3 阻断性判断：**否**

- 单字符显示异常，不改变语义（读者仍能理解"人口增长"）。
- **已在新快照中自然消失**，证明它随上游数据漂移，不是代码固定缺陷。
- 评审期强行加过滤（如 `replace("\ufffd", "")`）属于掩盖症状，且可能误删正常内容。

### 3.4 建议处置

- 评审期**不修**，与 R2 一并列为赛后项。
- 赛后可在 `_clip()` 统一清洗时顺带剔除 U+FFFD（与方案 B 同一处改动，合并实施）。
- 提交日验收时**顺手肉眼扫一遍**当天快照是否有乱码；若出现在显眼位置，再按值班卡决定是否补跑。
