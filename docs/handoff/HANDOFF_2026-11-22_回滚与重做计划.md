## 二、为什么会回滚——今晚方案的问题复盘

目标是"正式站和临时站一模一样"，今晚的做法是在现有 Flask 管线上打补丁：
1. 富化数据预置为 `data/brief_<日期>.json`（骗过管线缓存层）
2. `_is_enriched()` 防覆盖保护（阻止管线刷新）
3. 补 `/assets/` 静态路由

**用户验收结果：完全不一样，要求整体回滚重做。** 问题定性：
- 方案是在"管线生成器不产出富化字段"的地基上叠补丁，缓存命中/兜底/刷新三条路径的状态组合太多，行为不可预期（今晚就实际发生了三次"线上和预期不一致"）
- 每次补救都靠再加一层特殊判断，复杂度滚雪球，这不是能交付给队友维护的方案

## 三、明天重做的建议方向（先和饶子翔对齐再动手）

**核心决策：让正式站也变成"静态托管"架构，彻底绕开 Flask 管线的数据路径。**

方案 A（推荐，最简单）：
- 正式站不再让 app.py 动态生成 data.js；改为直接静态 serve `demo/`（CloudBase Hosting 静态托管，或 CloudRun nginx 静态服务）
- 每日数据更新 = 生成新的 `demo/data.js` → 部署。没有缓存层、没有兜底分支、没有刷新竞争——和临时站**天然一模一样**
- 废弃（或仅保留作数据抓取工具）app.py 的 /data.js 动态路径
- 架构验证点：Hosting 已删过旧站可以重建；或 CloudRun 用 nginx 镜像 serve 静态文件

方案 B：保留 CloudRun，但 app.py 砍掉动态生成，只留静态文件服务（等于 A 用 Flask 实现，没必要）

**重做时必须向饶子翔确认清楚的点：**
1. "一模一样"的具体验收标准：数据徽章显示什么（当日缓存/示例数据？）、提示语怎么写
2. 每日更新接受什么形态：纯静态每日一版（推荐）还是仍要"实时 API + 兜底"
3. v2.8 的富化字段（看山/判决卡/跨平台核验）是每天都要新生成，还是作为功能点演示即可
4. 回滚期间（038 状态）线上是 11-15 旧兜底数据 + 无 v2.8 功能，确认这是用户接受的临时态
